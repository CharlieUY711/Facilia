# Objetivo

Definir cómo los usuarios acceden a FACILIA y qué pueden hacer dentro de cada portal.

Debe quedar resuelto:

* identidad;
* autenticación;
* organizaciones;
* roles;
* permisos;
* alcance de información.

---

# Principio fundamental

FACILIA no administra usuarios aislados.

Administra:

```text
Persona

↓

Usuario

↓

Organización

↓

Rol

↓

Permisos
```

---

# 1. Fuente de identidad

El sistema debe consumir:

```text
DIRECTORY
```

como Master Data Management.

Directory administra:

* Personas.
* Organizaciones.
* Relaciones.
* Ubicaciones.
* Roles base.

Los portales consumen esa información.

---

# 2. Modelo de Usuario

Definir entidad:

## PortalUser

Representa una identidad habilitada para ingresar.

Campos:

* id;
* directory_person_id;
* email;
* teléfono;
* estado;
* último acceso;
* organización principal.

Estados:

```text
ACTIVE

INVITED

BLOCKED

DISABLED
```

---

# 3. Relación Usuario - Organización

Un usuario puede pertenecer a una o varias organizaciones.

Modelo:

```text
User

   |

OrganizationMembership

   |

Organization
```

---

Ejemplo:

Empleado FACILIA:

```text
Juan

↓

FACILIA SAS

↓

Rol:
Operario
```

---

Cliente:

```text
María

↓

ABC SA

↓

Rol:
Administrador Cliente
```

# 4. Roles del sistema

Definir RBAC.

---

# Roles internos FACILIA

## Platform Admin

Acceso total.

---

## Operations Manager

Puede:

* planificar;
* supervisar;
* consultar operaciones.

---

## Supervisor

Puede:

* administrar equipos;
* revisar ejecución;
* gestionar incidencias.

---

## Employee

Puede:

* consultar tareas propias;
* reportar ejecución;

# Roles cliente

## Customer Admin

Puede:

* administrar usuarios cliente;
* consultar contratos;
* consultar servicios.

---

## Customer User

Puede:

* consultar información autorizada.

# 5. Modelo de permisos

No controlar solo por rol.

Implementar:

```text
Role

+

Permission

+

Scope
```

---

Ejemplo:

Permiso:

```text
view_work_orders
```

Scope:

```text
OWN_ASSIGNED
```

Resultado:

El empleado solo ve sus órdenes.

---

Ejemplo:

Supervisor:

```text
view_work_orders

Scope:

TEAM
```

---

Cliente:

```text
view_contracts

Scope:

OWN_ORGANIZATION
```

# 8. Invitaciones

Flujo:

```text

↓

Invita usuario

↓

↓

Cuenta activa
```

---

# 9. Seguridad Multi Tenant

Reglas obligatorias:

Toda consulta debe validar:

```text
organization_id
```

Nunca permitir:

* acceso cruzado;
* consulta global desde cliente;
* exposición de evidencias.

---

# 10. Auditoría

Registrar:

* login;
* invitación;
* cambio rol;
* bloqueo;
* permisos modificados.

Entidad:

```text
AccessAuditLog
```
