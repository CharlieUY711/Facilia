# PROMPT COM-05 — Integración Completa COM + Operations y Ciclo Operativo de Comunicación

> **Rol**
>
> Actúa como un **Enterprise Integration Architect** especializado en plataformas SaaS empresariales, Field Service Management (FSM), Workflow Automation, DDD, arquitectura orientada a eventos y sistemas multi-tenant.
>
> El módulo:
>
> # COM — Communications Hub
>
> ya cuenta con:
>
> * COM-00 — Documento Maestro Funcional.
> * COM-01 — Modelo de Dominio y Persistencia.
> * COM-02 — Backend Core + Integración Twilio.
> * COM-03 — Motor de Plantillas y Automatizaciones.
> * COM-04 — Inbox, Evidencias, Respuestas e Incidentes.
>
> Esta etapa integra COM con el ciclo operacional completo de FACILIA.
>
> **No rediseñar Operations.**
>
> **No crear nuevas responsabilidades dentro de COM.**
>
> **No modificar entidades propietarias de otros módulos.**
>
> COM debe actuar como capa de comunicación y trazabilidad.

---

# Objetivo

Cerrar la integración entre:

```text id="j4m7kp"
Operations

+

COM

+

Library

+

GEO (preparado)
```

permitiendo que una Orden de Trabajo tenga un ciclo completo:

```text id="z9v3cc"
Planificar

↓

Asignar

↓

Comunicar

↓

Confirmar

↓

Ejecutar

↓

Evidenciar

↓

Cerrar
```

---

# Principio fundamental

Operations controla el trabajo.

COM controla la comunicación.

La información debe viajar mediante eventos.

---

# 1. Eventos consumidos desde Operations

Implementar listeners para:

---

## WorkOrderCreated

Acción:

Preparar comunicación si corresponde.

---

## WorkOrderAssigned

Acción:

Enviar asignación al empleado.

Mensaje:

```text id="v0x7py"
Nueva tarea asignada

Cliente:
{{cliente}}

Servicio:
{{servicio}}

Horario:
{{hora}}
```

---

## WorkOrderUpdated

Acción:

Informar cambios.

Ejemplo:

* cambio horario;
* cambio ubicación;
* cambio instrucciones.

---

## WorkOrderCancelled

Acción:

Enviar cancelación.

---

## WorkOrderCompleted

Acción:

Solicitar cierre/evidencia.

---

# 3. Confirmación del empleado

Cuando COM recibe:

```text id="z8k8q5"
CONFIRMAR
```

Generar evento:

```text id="h2k9v6"
EmployeeConfirmedAssignment
```

Operations puede actualizar:

```text id="f0x8m3"
confirmation_status
```

---

# 4. Rechazo de asignación

Empleado:

```text id="x5n2da"
NO PUEDO
```

Generar:

```text id="7d1s0m"
EmployeeRejectedAssignment
```

Enviar alerta:

* supervisor;
* planificación.

# 7. Vista operacional preparada

Crear APIs para que Operations pueda consultar:

---

## Comunicación de una OT

```http id="7k1f8d"
GET /api/com/work-orders/{id}/communications
```

Retorna:

* mensajes;
* confirmaciones;
* evidencias;
* incidentes.

---

## Estado comunicación

```http id="9s5n2c"
GET /api/com/work-orders/{id}/communication-status
```

Ejemplo:

```json
{
"assigned": true,
"confirmed": true,
"evidence_received": true
}
```

# 8. Auditoría operacional

Cada comunicación debe responder:

* quién;
* cuándo;
* para qué orden;
* qué resultado tuvo.

Ejemplo:

```text id="k0p8vz"
OT-12345

Empleado:
Juan

Mensaje:
Asignación enviada

Estado:
DELIVERED
```
