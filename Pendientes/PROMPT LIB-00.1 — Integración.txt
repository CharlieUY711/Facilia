# PROMPT LIB-00.1 — Integración Arquitectónica de Library dentro de FACILIA

> **Rol**
>
> Actúa como un **Arquitecto de Software Enterprise Senior**, especialista en DDD, Clean Architecture, plataformas SaaS multi-tenant, gestión documental empresarial y diseño de módulos desacoplados.
>
> Este documento es una extensión de **LIB-00 — Arquitectura Funcional del Módulo Library**.
>
> En esta etapa **no se genera código**.
>
> El objetivo es definir cómo Library se integra dentro de la plataforma FACILIA sin crear dependencias incorrectas ni acoplamiento entre módulos.

---

# Contexto

FACILIA es una plataforma empresarial orientada a la gestión de servicios de:

* limpieza profesional;
* mantenimiento;
* continuidad operativa;
* gestión de clientes;
* operaciones;
* documentación empresarial.

La plataforma utiliza una arquitectura modular basada en:

* Next.js App Router.
* TypeScript Strict.
* Supabase.
* PostgreSQL.
* DDD.
* Clean Architecture.
* Repository Pattern.
* Arquitectura Charlie Compliant.

Cada módulo representa un **bounded context independiente**.

---

# Objetivo

Definir cómo el módulo **Library** se integra con todos los módulos actuales y futuros de FACILIA.

Library debe convertirse en la capa documental transversal de la plataforma.

---

# Principio fundamental

## Los módulos no almacenan archivos.

Los módulos solamente gestionan información de negocio.

Los documentos pertenecen a Library.

Ejemplo incorrecto:

```text
Quotation

- proposal_pdf
- image_file
- contract_file
```

Ejemplo correcto:

```text
Quotation

      |
      |
DocumentLink

      |
      |
Library Document
```

# Document Ownership

Definir claramente:

¿Quién es dueño del documento?

Regla propuesta:

## Library es dueña del documento físico.

Library administra:

* archivo;
* ubicación;
* permisos;
* acceso;
* historial.

El módulo origen administra:

* contexto;
* relación;
* significado empresarial.

# Seguridad e identidad

Definir la relación entre:

* Usuario.
* Organización.
* Rol.
* Documento.

Regla:

Library controla acceso al documento.

El módulo de negocio solamente solicita acceso.

Ejemplo:

Un usuario abre un contrato.

Proceso:

```text
Contrato solicita documento

↓

Library valida permisos

↓

Library devuelve acceso permitido
```

# Reglas de diseño

Library:

NO debe saber:

* qué es un contrato;
* qué es una cotización;
* qué es una orden de trabajo.

Los módulos:

NO deben saber:

* dónde se guardan archivos;
* cómo funcionan los permisos;
* cómo funciona Storage.
